# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a working Requester-facing ticketing MVP on top of the Lab 1 vertical
slice: a Requester (simulated via a temporary Development Requester selector)
can create an IT support ticket with supporting attachments, find it again in
My Tickets via search/filter/sort/pagination, open its read-only Ticket
Detail, and manage (add/soft-remove) permitted attachments — all while one
Requester's tickets remain invisible and inaccessible to another Requester.

## 2. Stakeholder Request Interpretation

The IT department wants a professional, responsive ticket-submission
experience for end users, ahead of real authentication (arriving in Lab 3).
Because there is no login yet, the app must let a tester explicitly pick
which seeded Requester identity is "logged in" for the current session, and
every ticket/attachment operation must behave as if that Requester were
really authenticated — including strict ownership isolation between
Requesters. The visual language introduced this sprint (Zen Green theme,
field/badge/validation conventions) must be reusable in later labs.

## 3. Scope

### Included
- Development Requester Selection screen (testing-only "login" simulator)
- Selected-Requester context: display, Change Requester action, reload of
  requester-scoped data on switch
- Create Ticket screen and API (`POST /api/tickets`)
- My Tickets screen and API: search, filter, sort, pagination
  (`GET /api/tickets`)
- Requester Ticket Detail screen (read-only) and API
  (`GET /api/tickets/:id`)
- Attachment lifecycle: upload, list/metadata, download, soft removal
- Reference data: Categories, Related Systems, active Development Requesters
- Zen Green UI specification and reusable component/state conventions
- Ownership enforcement (a Requester can never read or act on another
  Requester's Ticket or Attachment)
- Automated tests: unit, API/integration, UI component, responsive/visual,
  and E2E, all traceable to Acceptance Criteria

### Excluded
- Authentication and security: real login, logout, passwords, hashing,
  sessions, tokens, or role-based authorization. The Development Requester
  selector is a testing mechanism only.
- IT Staff workflow: dashboard, queue, claiming/reassigning tickets, IT
  Priority, ticket ownership by staff.
- Ticket collaboration/work tracking: Public Comments, Internal Notes,
  Actions Taken.
- Ticket lifecycle beyond initial `New` status: resolution, closing,
  reopening, cancelling.
- Administration: user/Requester/role/reference-data management screens.

## 4. Functional Requirements

- FR-01: The system shall allow selecting an active Development Requester
  before any ticket screen is accessible.
- FR-02: The system shall allow a Requester to create a Ticket with Category,
  Related System, Summary, Description, Requested Priority, and optional
  Attachments.
- FR-03: The system shall generate a unique, backend-assigned Ticket Number
  upon successful creation and return it to the client.
- FR-04: The system shall list only the selected Requester's own Tickets in
  My Tickets.
- FR-05: The system shall support searching My Tickets by Ticket Number and
  Summary.
- FR-06: The system shall support filtering My Tickets by Category,
  Requested Priority, and Current Status.
- FR-07: The system shall support sorting My Tickets by at least Created
  Date and Last Updated.
- FR-08: The system shall paginate My Tickets results with a documented
  default and maximum page size.
- FR-09: The system shall allow retrieval of one Ticket's detail only when
  it belongs to the selected Requester; otherwise it shall return a
  not-found-style response (never leak existence to a non-owner).
- FR-10: The system shall allow adding a permitted Attachment (JPG, JPEG,
  PNG, WEBP, PDF; ≤5 MB; ≤5 active Attachments per Ticket) to an owned
  Ticket.
- FR-11: The system shall allow downloading only active (non-removed)
  Attachments belonging to an owned Ticket.
- FR-12: The system shall allow soft-removing an owned, active Attachment
  with a required removal reason; removed Attachments remain visible as
  metadata but are not downloadable.
- FR-13: The system shall preserve entered Create Ticket field values in the
  UI after a validation or submission failure.
- FR-14: The system shall show explicit loading, empty, no-results, and
  failure states on every screen that fetches data.

## 5. Business Rules

**Ticket defaults and system-generated values**
- BR-01: The official Ticket Number is generated by the backend and must be
  unique (format: `TKT-<year>-<zero-padded sequence>`, e.g. `TKT-2026-000123`).
- BR-02: A new Ticket begins with Current Status `New`.
- BR-03: Ticket Date (`createdAt`) is system-generated at creation time and
  is read-only.
- BR-04: IT Priority is not set at creation; it remains unset (`null`) until
  IT Staff triage it in a later lab.
- BR-05: Ticket Owner is not assigned at creation; it remains unset until
  IT Staff claim it in a later lab.

**Development Requester selection and switching**
- BR-06: Lab 2 uses a Development Requester selector instead of login. The
  selected identity is for testing only and is not authentication.
- BR-07: Only active Development Requesters appear in the selector; inactive
  Requesters are excluded from the list and cannot be selected.
- BR-08: The selected Requester persists for the current browser session
  (e.g. in memory/session storage) until changed via "Change Requester" or
  the tab is closed.
- BR-09: Switching the selected Requester immediately invalidates and
  reloads all requester-scoped views (My Tickets, any open Ticket Detail
  redirects to My Tickets or shows an ownership error if still open).
- BR-10: If no active Development Requesters exist, the selector shows an
  empty state and blocks entry into any ticket screen.

**Ticket ownership**
- BR-11: Every Ticket belongs to exactly one Requester (`requesterId`),
  captured from the selected Development Requester at creation time and
  never editable afterward.
- BR-12: All read and write operations on a Ticket or its Attachments are
  authorized against the selected Requester's id on the backend, not
  trusted from client-supplied values beyond the session selection.
- BR-13: A Requester attempting to access another Requester's Ticket
  (detail, attachment list, download, or removal) receives a safe
  not-found-style response; no data about the other Ticket is disclosed.

**Search, filtering, sorting, and pagination**
- BR-14: Search matches Ticket Number (exact or partial) and Summary
  (case-insensitive partial match).
- BR-15: Filters (Category, Requested Priority, Current Status) are
  combinable (AND logic) and optional; omitting a filter means "all".
- BR-16: Default sort is Created Date descending (newest first) when no
  sort parameter is supplied.
- BR-17: Default page size is 10; maximum permitted page size is 50; an
  out-of-range or non-numeric page/pageSize value falls back to the
  default rather than erroring.

**Validation and duplicate-submission prevention**
- BR-18: Ticket Summary is required, trimmed, 5–120 characters.
- BR-19: Ticket Description is required, trimmed, 10–2000 characters.
- BR-20: Category and Related System are required and must reference
  existing active reference-data rows.
- BR-21: Requested Priority is required and must be one of `LOW`, `MEDIUM`,
  `HIGH`.
- BR-22: The Submit button is disabled while a creation request is in
  flight, preventing duplicate submissions from repeated clicks.
- BR-23: Client-side validation mirrors backend validation, but the backend
  is the source of truth; the backend re-validates every field
  independently of client checks.

**Failure behavior and data retained after errors**
- BR-24: On a validation failure (400), all previously entered field values
  are preserved in the UI; only the invalid field(s) show inline error
  messages.
- BR-25: On an unexpected server/network failure during Create Ticket, the
  UI shows a safe generic error message, preserves entered values, and does
  not claim the Ticket was created unless a 201 response with a Ticket
  Number was actually received.
- BR-26: If Ticket creation succeeds but a selected attachment fails to
  upload, the Ticket is still considered created (Ticket Number stands);
  the UI reports which attachment(s) failed and lets the Requester retry
  the attachment upload from the resulting Ticket Detail screen.

**Attachment upload, download, and soft removal**
- BR-27: Allowed Attachment types are JPG, JPEG, PNG, WEBP, and PDF only;
  other types are rejected client-side (when detectable) and backend-side
  (always).
- BR-28: Maximum Attachment size is 5 MB per file; oversized files are
  rejected with a clear error before/at upload.
- BR-29: Maximum 5 active Attachments per Ticket; the 6th active upload
  attempt is rejected with a clear message (soft-removed Attachments do not
  count toward this limit).
- BR-30: Removing an Attachment is a soft removal: the row is flagged
  removed (with timestamp and reason) but never physically deleted from
  storage or the database in Lab 2.
- BR-31: A removed Attachment remains visible in the UI as metadata (name,
  size, type, removal date/reason) but its download/preview action is
  disabled and the backend rejects direct download requests for removed
  Attachments (403/404-style safe response).
- BR-32: Removing an Attachment requires the Requester to confirm the
  action and provide a short removal reason (required, trimmed, 3–200
  characters).
- BR-33: Stored filenames are sanitized/randomized on disk; the original
  filename is preserved only as metadata for display.

**Inactive Requesters**
- BR-34: An inactive Development Requester is excluded from the selector
  entirely (BR-07) and, if somehow already selected in an existing session,
  is treated as if no Requester is selected on the next data request
  (forcing re-selection).

**Empty and no-results states**
- BR-35: My Tickets shows a distinct "no tickets yet" empty state when the
  Requester owns zero Tickets overall, versus a distinct "no results match
  your filters" state when Tickets exist but the current
  search/filter/sort combination returns zero rows.
- BR-36: The Development Requester selector shows a distinct empty state
  (BR-10) versus a distinct API-failure state when the active-Requester
  list cannot be loaded.

**Ticket Detail access**
- BR-37: Requester Ticket Detail is read-only in Lab 2: no status changes,
  no editing of header fields, no Public Comments, Internal Notes, or
  Actions Taken.
- BR-38: Ticket Detail is reachable only via My Tickets or a direct URL to
  an owned Ticket id; a direct URL to a non-owned or non-existent Ticket id
  shows the same safe "not found" experience (BR-13).

**Transition to real authentication in Lab 3**
- BR-39: The Development Requester selection mechanism, its client-side
  storage, and its backend trust model are isolated behind a single
  context/service boundary so that Lab 3 can replace them with real
  authentication without redesigning Ticket/Attachment business logic.
- BR-40: No password, session token, or credential concept is introduced in
  Lab 2; `RequesterUser.id` is the only identity concept, explicitly
  documented as non-authenticated.

## 6. UI Specification Summary

See `docs/lab-02/ui-spec.md` for full detail. Summary:

- **Application shell**: TokTickIT title, My Tickets / Create Ticket nav,
  selected-Requester display with a "Change Requester" action, responsive
  mobile nav (collapses to a menu below 768px).
- **Development Requester Selection**: full-screen card, dropdown of active
  Requesters, explanatory "testing only" text, Continue button, loading/
  empty/error states, keyboard-accessible.
- **Create Ticket**: system-generated fields visually distinct (read-only
  shading) from editable fields; Summary/Description given generous width;
  Attachments section below main fields; primary (Submit) and secondary
  (Cancel) actions at the bottom; busy state on Submit; inline validation
  messages under each field.
- **My Tickets**: search bar, filter row (Category/Priority/Status),
  sortable column headers, paginated table (desktop) collapsing to cards
  (mobile), badges for Requested Priority/Current Status, Create Ticket
  shortcut, Clear Filters action.
- **Ticket Detail**: read-only header fields grouped logically, separate
  Attachments panel with add/download/remove actions per active file and
  greyed-out removed entries, Back to My Tickets navigation.
- **Zen Green tokens**: primary `#006B3C`, secondary `#0B7A46`, pale green
  `#EAF6EF`, page background `#F5F7F6`, error dark red, warning amber,
  success green — applied consistently to buttons, badges, fields, and
  alerts as defined in Section 7 of the Lab 2 handout.

## 7. Data Changes

New/extended Prisma models (see `server/prisma/schema.prisma` for the
authoritative source once implemented):

- `RequesterUser`: `id`, `name`, `email` (unique), `isActive` (default
  `true`), `createdAt`.
- `Category` (from Lab 1, reused): `id`, `name` (unique), `createdAt`.
- `RelatedSystem`: `id`, `name` (unique), `isActive` (default `true`),
  `createdAt`.
- `Ticket`: `id`, `ticketNumber` (unique, backend-generated), `requesterId`
  (FK → RequesterUser), `categoryId` (FK → Category), `relatedSystemId`
  (FK → RelatedSystem), `summary`, `description`, `requestedPriority`
  (enum: `LOW`/`MEDIUM`/`HIGH`), `itPriority` (enum, nullable),
  `currentStatus` (enum, default `NEW`), `ticketOwnerId` (nullable, FK,
  unused in Lab 2), `resolutionSummary` (nullable, unused in Lab 2),
  `createdAt`, `updatedAt`.
- `Attachment`: `id`, `ticketId` (FK → Ticket), `originalFilename`,
  `storedFilename` (sanitized/randomized), `mimeType`, `sizeBytes`,
  `isRemoved` (default `false`), `removedAt` (nullable), `removalReason`
  (nullable), `uploadedAt`.

**Indexes/constraints**: unique index on `Ticket.ticketNumber`; unique index
on `RequesterUser.email`; index on `Ticket.requesterId` (ownership lookups
and My Tickets listing); index on `Ticket.currentStatus`,
`Ticket.categoryId` (filtering); index on `Attachment.ticketId`.

**Soft removal** is represented by `Attachment.isRemoved` +
`removedAt`/`removalReason` — no physical deletion in Lab 2.

## 8. API Contract

See `docs/lab-02/api-spec.md` for full request/response shapes. Endpoints:

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/categories` | List active Categories |
| GET | `/api/related-systems` | List active Related Systems |
| GET | `/api/requesters` | List active Development Requesters |
| POST | `/api/tickets` | Create a Ticket for the selected Requester |
| GET | `/api/tickets` | Paginated, searchable, filterable, sortable list of the selected Requester's own Tickets |
| GET | `/api/tickets/:id` | Retrieve one owned Ticket's detail |
| POST | `/api/tickets/:id/attachments` | Upload an Attachment to an owned Ticket |
| GET | `/api/tickets/:id/attachments` | List Attachment metadata (active + removed) for an owned Ticket |
| GET | `/api/attachments/:id/download` | Download one active, owned Attachment |
| DELETE | `/api/attachments/:id` | Soft-remove one active, owned Attachment (body includes reason) |

The selected Requester id is passed via a request header (e.g.
`X-Requester-Id`) for Lab 2's testing mechanism; every endpoint above
re-validates ownership against this header server-side (BR-12).

## 9. Acceptance Criteria

- AC-01: Given valid Ticket data, when the Requester submits the form, then
  one Ticket is saved and the official Ticket Number is displayed.
- AC-02: Given no Development Requester is selected, when the user attempts
  to open My Tickets, then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to
  Requester A is requested by id, then the Ticket data is not returned.
- AC-04: Given the Summary field is empty, when the Requester submits
  Create Ticket, then a field-level error is shown and no API call is made.
- AC-05: Given a valid Ticket and one valid attachment, when the Requester
  completes the full submission flow at desktop, tablet, and mobile
  viewports, then the confirmation shows the official Ticket Number in all
  three.
- AC-06: Given an invalid file type is selected as an attachment, when the
  Requester attempts to add it, then a clear error is shown and the file is
  not uploaded.
- AC-07: Given the backend is unavailable, when the Requester submits
  Create Ticket, then a safe error state is shown and all entered field
  values remain in the form.
- AC-08: Given Requester A has 3 Tickets and Requester B has 2 Tickets, when
  Requester A views My Tickets, then only Requester A's 3 Tickets are
  listed.
- AC-09: Given My Tickets has more rows than one page, when the Requester
  changes page, sort, or a filter, then the list and pagination metadata
  update accordingly without page reload.
- AC-10: Given zero Tickets match the current search/filter combination,
  when results are displayed, then a "no results match your filters" state
  is shown, distinct from the zero-tickets-overall empty state.
- AC-11: Given an active Attachment on an owned Ticket, when the Requester
  clicks download, then the file downloads successfully.
- AC-12: Given a Requester soft-removes an Attachment with a reason, when
  the Ticket Detail is reloaded, then the Attachment appears as removed
  metadata and its download action is disabled.
- AC-13: Given a removed Attachment's id, when a download is attempted
  directly via the API, then the request is rejected safely.
- AC-14: Given a Ticket already has 5 active Attachments, when a 6th
  upload is attempted, then it is rejected with a clear message.
- AC-15: Given an inactive Development Requester, when the Requester
  selector loads, then that Requester does not appear in the dropdown.
- AC-16: Given no active Development Requesters exist, when the selector
  loads, then an empty state is shown and ticket screens remain
  inaccessible.
- AC-17: Given a Requester is selected, when "Change Requester" is used to
  switch to a different Requester, then My Tickets reloads to show only the
  new Requester's Tickets.
- AC-18: Given a Ticket creation request is in flight, when the Requester
  clicks Submit again, then no duplicate Ticket is created (button is
  disabled/busy).
- AC-19: Given the app is viewed at a mobile viewport (<768px), when My
  Tickets is open, then the layout has no horizontal scrolling and all
  actions remain reachable.
- AC-20: Given a keyboard-only user, when navigating the Development
  Requester Selection screen, then every control is reachable and operable
  via keyboard with a visible focus indicator.

## 11. Assumptions and Decisions

- Ticket Number format chosen as `TKT-<year>-<6-digit sequence>` (not fixed
  by the handout) — kept consistent with the illustrative screens in the
  handout (`TKT-2025-001234`).
- Selected-Requester identity is propagated via an `X-Requester-Id` request
  header rather than a query parameter, to keep it out of URLs/logs and to
  mirror how a real auth token will be sent in Lab 3 (eases the BR-39
  migration).
- Default My Tickets page size set to 10 (not specified by the handout);
  maximum 50 chosen to bound response size and query cost.
- Attachment storage in Lab 2 uses local disk (`server/uploads/`) rather
  than a cloud bucket, consistent with the "local web application" scope of
  Labs 1–4 (cloud deployment is explicitly deferred per the Lab 1 handout).
- IT Priority and Ticket Owner fields are included in the `Ticket` model
  now (nullable) to avoid a breaking migration in a later lab, even though
  they are not set or displayed as editable in Lab 2.
